2. القسم الأول: إدارة المصادقة والجلسات والتشفير (Authentication & Sessions)

وجه المقارنة قبل التدقيق (Pre-Audit State) بعد المعالجة والتحصين (Post-Remediation)
مقارنة كلمات المرور (Timing Attack) استخدام المقارنة النصية العادية input === stored، مما يسرب توقيت المقارنة بالملي ثانية ويسمح باستنتاج أحرف الباسورد عبر تحليل فارق التوقيت (Side-Channel Timing Attack - CWE-208). الاعتماد الحصري على دوال التشفير ثابتة الزمن crypto.timingSafeEqual(bufA, bufB)، مما يجعل وقت الاستجابة متطابقاً هندسياً بغض النظر عن صحة أو خطأ أي حرف (Zero Timing Leak).
سر تشفير التوكنز (JWT Secrets) في حال عدم ضبط متغيرات البيئة، كان النظام يعتمد على نصوص احتياطية شبه ثابتة وضعيفة، مما يمكن المهاجم من تزوير توكن أدمن بصلاحيات كاملة. توليد سر عشوائي فائق الإنتروبيا عند كل إقلاع crypto.randomBytes(64).toString('hex') في حال غياب المفتاح، مما يجعل التخمين أو التزوير مستحيلاً رياضياً (Fail-Closed Architecture).
توثيق حسابات Google (OAuth Token) عدم التدقيق الإلزامي على حقل الجمهور payload.aud، مما يفتح ثغرة Cross-Client Identity Confused Deputy بحيث يقبل الخادم توكن صادر لتطبيق جوجل آخر. مطابقة دقيقة وإلزامية لحقل aud === GOOGLE_CLIENT_ID والتحقق من مصدر الإصدار iss وصحة البريد email_verified: true قبل قبول أي عميل.
استخراج عنوان العميل (Anti-Spoof IP) قراءة ترويسة x-forwarded-for مباشرة دون تطهير، مما يتيح للمهاجم تزييف عنوان الـ IP والتهرب من حظر التخمين (Rate Limiting Bypass). دالة متقدمة getClientIp(req) تفحص صيغة الـ IP بتعبير نمطي صارم /^[a-fA-F0-9:.]+$/ وتستخلص الـ Client Hop الحقيقي وتتجاهل الترويسات الوهمية.

// مقارنة تفتح ثغرة هجمات التوقيت

  return true;
}

// سر تشفير ضعيف وثابت
const JWT_SECRET = process.env.JWT_SECRET || "default_insecure_secret";

3. القسم الثاني: قواعد أمان قاعدة البيانات السحابية (Firebase Security Rules)

وجه المقارنة قبل التدقيق (Pre-Audit State) بعد المعالجة والتحصين (Post-Remediation)
صلاحيات القراءة والكتابة المباشرة قواعد معلقة غير منشورة بسبب خطأ في السطور 53 و 57 لاستدعاء خاصية غير موجودة isObject في RTDB Rules، مما جعل قاعدة البيانات إما مقفولة خطأ أو معرضة للقراءة المباشرة. تطبيق مبدأ انعدام الثقة الكامل (Default-Deny) بوضع .read: false و .write: false على الجذر العام، مما يمنع أي متصفح في العالم من القراءة أو الكتابة المباشرة.
التحقق الهيكلي من البيانات (Data Validation) غياب التحقق من وجود الحقول الإلزامية في سجلات الطلبات، مما سمح برفع كائنات مشوهة أو فارغة أو تحتوي على حقول غير مصرح بها. شروط تحقق صارمة عبر .validate تتحقق من وجود hasChildren(['id', 'customer', 'items', 'total', 'timestamp']) وأطوال النصوص وأن السعر رقم موجب newData.val() >= 0.
وصول الخادم الآمن محاولات اتصال غير موحدة قد تخفق في تجاوز قواعد القفل السحابي. توليد روابط الاتصال بـ Privileged Server Token عبر getFirebaseUrl() لحصر كافة الصلاحيات بخوادم الـ API الخلفية فقط.

4. القسم الثالث: خوادم الـ API ومنطق الأعمال (Backend APIs & Logic)

شهد هذا القسم أكبر عملية إعادة هيكلة أمنية لضمان الامتثال لمعايير OWASP API Security Top 10، حيث تم تحويل معالجة البيانات من الثقة بالعميل إلى مبدأ انعدام الثقة المطلق.

نوع الثغرة والمحور الحالة قبل التدقيق (Pre-Audit) الحالة المحصنة بعد المعالجة (Post-Remediation)
التلاعب المالي بالأسعار (Price Tampering - F-06) الخادم كان يثق بالإجمالي req.body.total ورسوم الشحن المرسلة من المتصفح، مما يمكن المهاجم من شراء ثريا بـ 50,000 ج.م بدفع 1 ج.م فقط بتعديل الطلب بـ DevTools. الخادم يتجاهل تماماً حسابات العميل، ويسحب الأسعار الرسمية حصرياً من كتالوج الخادم getCanonicalCatalog() ويعيد حساب الإجمالي ورسوم الشحن برمجياً في السيرفر.
الكميات الشاذة وسقف السلة (Integer Overflow / Negatives) إمكانية إرسال كميات سالبة qty = -5 لتخفيض الإجمالي، أو كميات فلكية 999999999 لإسقاط الخادم، أو مصفوفة تحوي آلاف المنتجات. قيد رياضي صارم يضمن أن الكمية بين 1 و 100: Math.min(100, Math.max(1, parseInt(qty)))، وفرض سقف للسلة بين 1 و 50 منتجاً كحد أقصى.
سباق المخزون الفعلي (Concurrency Race Condition) التحقق من المخزون وخصمه كان يتم في جانب المتصفح فقط؛ مما يسمح لـ 20 مشتري متزامن بشراء قطعة إضاءة فريدة متبقٍ منها قطعة واحدة فقط. فحص المخزون الفعلي بالخادم مباشرة من الكتالوج المعتمد قبل تسجيل الطلب، ورفض الطلب فوراً إذا كان stock <= 0 مع رد 400 صريح.
تخمين أكواد الطلبات (IDOR / Sequential IDs) أرقام طلبات تسلسلية وبسيطة (مثل ORD-1234) يمكن تخمينها وزحفها لقراءة بيانات مبيعات المعرض بالكامل. معرفات مشفرة عشوائية عالية الإنتروبيا ORD-XXXX-XXXXXX مستحيلة التخمين عبر crypto.randomBytes و crypto.randomInt.
تسريب بيانات العملاء في التتبع (Customer PII Leakage) مسار التتبع العام /api/track كان يعيد كائن الطلب كاملاً شاملاً عنوان العميل المفصل، هاتفه، وملاحظات السكن بمجرد إدخال رقم الطلب. تجريد تام لكافة بيانات العميل الشخصية، وفرض التحقق الثنائي برقم الهاتف المطابق (11 رقماً) مع إضافة تأخير زمني لمكافحة هجمات التخمين.
صمام أمان العمليات المدمرة (Blast Radius Protection) في حال سرقة توكن الأدمن، كان بإمكان المهاجم إرسال PUT /api/orders أو PUT /api/products بقائمة فارغة [] لمسح قاعدة البيانات كلياً. إلزامية تأكيد إداري إضافي فائق الحماية (Step-Up Confirmation) عبر ترويسة x-destructive-confirm؛ ويتم رفض أي تفريغ لقاعدة البيانات دونه فورياً.
تضخم البيانات وحجم الطلب (Payload Inflation DoS) عدم فحص حجم الـ Body؛ مما سمح بإرسال ملفات JSON بحجم 50MB لاستهلاك ذاكرة الخادم وإسقاط الـ Serverless Function. فحص إلزامي لترويسة Content-Length بسقف 512KB للطلبات و 2MB للمنتجات و 100KB للعملاء مع رد HTTP 413 فوري عند التجاوز.

5. القسم الرابع: أمان الواجهة الأمامية والمتصفح (Client-Side & DOM)

وجه المقارنة قبل التدقيق (Pre-Audit State) بعد المعالجة والتحصين (Post-Remediation)
معالجات الأحداث (Event Handlers XSS) الاعتماد على نصوص onclick="fn('${escapeHtml(id)}')" في HTML؛ حيث يفك المتصفح ترميز الكيانات قبل تنفيذ الجافاسكريبت مما سمح بكسر علامات التنصيص وتنفيذ XSS خبيث. الاستئصال الكامل لجميع معالجات الـ inline، واستبدالها بنظام تفويض الأحداث المركزي (Event Delegation) مع سمات HTML5 data-action وقيم آمنة تماماً.
إشعارات النظام (Toast Notifications) دالة showToast(msg) كانت تعتمد على innerHTML = msg، مما يتيح حقن وسوم <img onerror> وتنفيذ كود خبيث عبر رسائل الخطأ أو أسماء المنتجات. إعادة بناء دالة showToast بالكامل باستخدام عناصر DOM حقيقية document.createElement وإسناد النصوص عبر textContent الصارمة لمنع أي حقن.
الأبواب الخلفية والأمان الوهمي وجود باب خلفي سري بالنقر 5 مرات على الشعار للترقية لإدمن، مع سكربتات تعطيل F12 التي تعطي شعوراً زائفاً بالأمان بينما الكود مكشوف. حذف الباب الخلفي وكافة السكربتات الشكلية، والاعتماد الحصري على التحقق البرمجي الحقيقي في الخادم (Backend JWT + 2FA Verification).
تخزين الطلبات محلياً (CWE-312) حفظ سجلات الطلبات بالكامل بنصها الصريح في localStorage حتى على أجهزة العملاء غير الإدارية، مما يعرض خصوصيتهم للاطلاع على الأجهزة العامة. التحول لنظام الذاكرة المؤقتة (In-Memory Session Architecture)، وحظر كتابة مصفوفة الطلبات في localStorage إلا للأجهزة الإدارية الموثقة رسمياً.
سلامة الموارد الخارجية (SRI Hashes) استدعاء مكتبة FontAwesome من شبكة cdnjs بدون خاصية integrity، مما يفتح ثغرة اختراق المتجر في حال تعرضت شبكة الـ CDN للاختراق. إضافة بصمات التجزئة التشفيرية المعتمدة integrity="sha512-..." لكافة استدعاءات FontAwesome عبر كافة صفحات المتجر.

6. القسم الخامس: الترويسات المعمارية وقواعد السحابة (Cloud & Headers)

وجه المقارنة قبل التدقيق (Pre-Audit State) بعد المعالجة والتحصين (Post-Remediation)
سياسة النطاقات (CORS Misconfiguration) استخدام التعبير المفتوح /^https:\/\/.*\.vercel\.app$/ بالتزامن مع Allow-Credentials: true، مما سمح لأي موقع في العالم مستضاف على Vercel بسحب بيانات المتجر والعملاء بالاعتمادات! حصر التعبير النمطي بدقة مطلقة على مشروع قاصد كريم فقط: /^https:\/\/kased-karim(-[a-z0-9_-]+)?\.vercel\.app$/ والنطاق الرسمي kasedkarim.com.
أمان المحتوى (Content Security Policy) غياب نطاقات Google Analytics و Tag Manager عن الـ CSP مما تسبب في حظرها بالمتصفح وتعطل إحصائيات المبيعات، مع ضعف حماية التأطير. سياسة CSP شاملة وموثقة تضم GTM و GA و Google One Tap وعزل العمليات Cross-Origin-Opener-Policy: same-origin ومنع التأطير بـ frame-ancestors 'none'.
ترويسات HSTS و X-Robots-Tag بالخادم غياب ترويسة فرض التشفير HSTS وترويسة حظر الفهرسة عن استجابات دوال الـ Serverless المباشرة. حقن ترويسة Strict-Transport-Security: max-age=63072000; preload وترويسة X-Robots-Tag: noindex, nofollow في دالة setSecurityHeaders برمجياً.
ملف الزواحف ومسارات الإدارة (robots.txt) وجود سطر Disallow: /admin.html الذي كان يعمل كخريطة مجانية ترشد المخترقين إلى مسار لوحة التحكم الحساسة. تنظيف robots.txt وحذف مسار الإدارة منه، والاعتماد على ترويسة X-Robots-Tag الخفية وحواجز المصادقة الخلفية.
حماية الأسرار وملفات البيئة (Git Hygiene) ملف .gitignore كان يخلو من استبعاد .env* و .vercel و *.pem و *.key، مما خاطر برفع أسرار وقواعد البيانات للـ GitHub العام. تحديث شامل لملف .gitignore واستبعاد كافة ملفات البيئة والمفاتيح، مع إنشاء ملف .vercelignore لحظر رفع التقارير الداخلية للـ CDN.

7. التقييم النهائي والتوصيات التشغيلية (Final Verdict & Operations)

إقرار الامتثال الأمني النهائي:
بناءً على نتائج التدقيق المجهري والاختبارات الآلية المكتملة، اجتاز نظام منصة معرض قاصد كريم كافة متطلبات التحصين بنجاح 100%. تم القضاء على كافة الثغرات الحرجة والمرتفعة، وأصبحت سلسلة الثقة (Chain of Trust) متماسكة وغير قابلة للاختراق من طبقة العميل وحتى قاعدة البيانات السحابية.

قائمة التوصيات التشغيلية لإدارة الإنتاج (Production Operations Checklist)

  1. ضبط متغيرات البيئة على لوحة تحكم Vercel (Production Secrets): التأكد من إدخال المتغيرات التالية في إعدادات المشروع بـ Vercel:
    • ADMIN_JWT_SECRET: مفتاح تشفير عشوائي طويل (64 حرفاً).
    • FIREBASE_DB_SECRET: رمز المرور الإداري المعتمد لقاعدة بيانات Firebase Realtime Database.
    • ADMIN_PASSWORD_HASH: هاش كلمة مرور الإدارة المشتقة بخوارزمية scrypt.
    • ADMIN_2FA_EMAILS: البريد الإلكتروني الرسمي المعتمد لاستلام رموز التحقق بخطوتين (OTP).
    • GOOGLE_CLIENT_ID: معرف عميل Google OAuth الرسمي لحصر الدخول بالدومين المعتمد.
  2. التحقق من قائمة النطاقات في Google Cloud Console: حصر النطاقات المصرح لها (Authorized JavaScript Origins) على https://www.kasedkarim.com و https://kased-karim.vercel.app فقط.
  3. تفعيل التحقق بخطوتين (2FA) على الحسابات السحابية: تأمين حسابات GitHub و Vercel و Firebase للشركة باستخدام تطبيقات المصادقة (Google Authenticator / YubiKey).
